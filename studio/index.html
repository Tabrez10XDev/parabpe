The race

Recorded traces replayed side by side on one clock. Same corpus, same vocabulary; lane A is the baseline.

… same merges.txt? checked at the finish

"Train race set" uses the Train form's corpus, vocab and threads: A = incr-serial on 1 thread (the baseline every speedup in this project is measured against), B = incr-batch on all threads with --merge-threads auto (phase 3 on the performance cores). Each lane's time is its real wall-clock trace; nothing is sped up or slowed down relative to another lane. A core tile is lit when one of the lane's threads ran a traced event there within the last 0.5% of the race clock (the core is sampled at the event's start: macOS cannot pin threads). The dashed tile marks work that is timed but not traced per event (the serial pre-tokenizer and the serial merge engines); the bar then moves evenly across the measured phase. Why a batch is exact

Sort the live pairs best-first. Take the longest prefix p[0..K) of pairwise token-disjoint pairs. Let c* be the count of its last member, T the pairs tied at c* after it, g the members counted above c*, and j the first member sharing a token with T.

k = max(min(K, j + 1), g, 1)

Theorem. From any training state, the next k merges of sequential BPE are exactly p[0], …, p[k−1], in that order. So one parallel round gives the same merges.txt, byte for byte.

Proof: merging never raises an old pair's count (Lemma 1), disjoint merges don't interact (Lemma 2), then induction on i. Full proof and counterexamples: docs/notes/batched_merging.md.
